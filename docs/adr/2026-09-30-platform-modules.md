# ADR: 以功能模块重写平台业务层

## 状态

已实施并通过本地验收，未部署。模块与阅读入口见
[整个平台阅读指南](../guides/platform-reading-guide.md)。

## 背景

当前平台支持账户、持久任务、文件和引用，但状态与调用边界混在较大的 Store、DO 和账本中。
目标是独立开发者能理解并维护的真实应用，不是增加术语或假设大型团队。

## 决策

- 保留现有技术栈、供应商和数据格式，以明确的功能模块组织平台。
- 前端将持久会话与任务观察分离；任务观察不是任务执行。
- 后端 DO 负责生命周期协调，存储事务、用量和事件执行分离。
- 账户中的身份、预算和文件配额分离，但保留单 DO 的串行一致性。
- 文件分析采用读取、构建原文上下文、生成三个真实阶段；不伪装成复杂规划。
- 输入类型优先于模型名称，防止指定文本模型绕过文件或图片处理。
- 浏览器继续使用持久事件游标轮询；供应商流使用 SSE，二者不能混称。
- 已验证的解析、哈希、Markdown 和检索算法继续复用。

## 收益与代价

收益：业务入口变短、单一职责易测试、失败边界可解释、历史数据无需迁移。

代价：模块与兼容入口增加；单账户 DO 仍有规模上限；轮询仍有请求成本；
保留旧结构意味着不能声称所有代码都从零编写。

## 未采用方案

- 全量删除并从 Git HEAD 重建：会丢失当前未提交能力和数据兼容约束。
- 引入微服务/队列/通用工作流：当前规模未证明收益，增加成本和学习负担。
- 无条件重试模型调用：结果不明时可能重复计费。
- 同时更换 UI、模型供应商和数据库：扩大验证和回滚风险。

## 验证

固定本地合成数据和模拟模型，比较重写前后功能、事件、存储、构建和性能。
生产部署和真实模型评测需要另行批准。

- 前端 148 项、Worker 326 项单元测试；lint、类型检查、生产构建和 dry-run 通过。
- 本地浏览器实际新建文本、图片、文件任务，验证取消、回放、账户隔离、
  上传丢失确认后的补传、原文引用、桌面与移动截图。
- 两位只读审查者发现的用量事件、账户晚响应、刷新竞态及模型匹配问题已修复并补测。
- 固定持久任务基准：读操作 34 → 33，事件、回放体积和写入量不变；
  CPU 中位数 2.6901 → 4.1318 ms，未证明性能改善。
