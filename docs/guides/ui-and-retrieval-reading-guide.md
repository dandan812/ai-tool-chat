# 新界面与文本检索：阅读和面试指南

这份指南对应本轮 UI 与文本检索改造，补充 `platform-reading-guide.md`。
只描述本地实现，不代表线上已经部署，也不是“所有代码从零手写”。

## 先读这六个文件

路径相对于项目根目录。

| 顺序 | 文件 | 一句话理解 |
| --- | --- | --- |
| 1 | `packages/frontend/src/views/Chat.vue` | 把导航、资源、消息和输入区组合起来，转发用户操作 |
| 2 | `packages/frontend/src/components/ChatMessages.vue` | 普通对话直接渲染，长对话按实际高度只渲染可见消息 |
| 3 | `packages/frontend/src/composables/useChatComposer.ts` | 管输入和附件，检查是否能发送，丢弃过期异步结果 |
| 4 | `packages/worker/src/utils/chunker.ts` | 按预算分割原文，但不删除空白、不拆开 emoji 或 CRLF |
| 5 | `packages/worker/src/retrieval/text/lexicalRanking.ts` | 给每个片段算可解释的词法匹配分数 |
| 6 | `packages/worker/src/retrieval/text/textRetriever.ts` | 建索引、读缓存、排序，然后按数量和正文预算选片段 |

先能把“一次输入怎样变成消息”和“一份文件怎样变成相关片段”说清楚。
业务流程中的账户、幂等任务、断点上传仍按上一份指南阅读。

## UI 为什么这样组织

聊天是主工作区，不是产品介绍页。侧栏管理会话；顶部资源面板管理任务、文件和用量；
消息区域独立滚动；输入区域留在底部，不随引用原文一起滚走。

每个组件主要负责一种展示。业务逻辑仍在 composable、Store 和 API 层，
不会为了重设计 UI 再复制一套账户或上传协议。

| 样式文件 | 只在这里改什么 |
| --- | --- |
| `styles/tokens.css` | 通用尺寸、字体、浅色主题颜色 |
| `styles/theme.css` | 深色主题变量覆盖 |
| `styles/base.css` | 基础元素、焦点和减少动态效果的规则 |
| `styles/workspace.css` | 工作台布局与组件外观 |

图标来自 Lucide；长列表采用 TanStack Vue Virtual 的动态测量，
Markdown、哈希和密码原语继续使用已有实现。依赖版本锁定，新增依赖会增加包体积。
这比把每条 Markdown 消息硬算成相同高度更可靠，但不是“零依赖”项目。

输入组件通过会话 ID 挂载独立实例。图片准备阶段禁止发送；
异步操作记录代次，组件离开或草稿重置后，旧结果不能回写。
发送还使用忙碌标记，避免等待附件解析期间重复提交。输入法确认文字的 Enter 不发送。

## 切块：先保证不丢资料

旧实现会反复估算剩余全文，并对每块 `trim()`；自然切点还可能越过预算。
新实现从左到右扫描，只考虑预算内的断点，返回原文的开始和结束偏移。

```text
原文
  → 扫描下一个不可拆单元
  → 检查估算 token 和字符两个限制
  → 在已能容纳的范围内选择段落、换行或标点断点
  → 保存 [startOffset, endOffset)
  → 从 endOffset 继续
```

`[start, end)` 表示包含 start、不包含 end。
偏移按 JavaScript 的 UTF-16 单元计算，不是字节，也不是 Unicode 字符数量。

核心约束：

1. 所有片段拼起来等于原文，包括首尾空白。
2. 每块不超过估算 token 预算和引用字符上限。
3. 不在合法代理对或 CRLF 中间切开；不规范的单独代理字符保留。
4. 如果一个不可拆单元也放不进预算，明确报错，而不是偷偷放宽预算。

token 数仍是兼容性估算，不是供应商 tokenizer。当前限制针对片段正文，
不能把正文估算当成包含提示词、JSON 转义、历史消息的实际计费 token。

## 检索：解释“为什么选它”

`lexicalRanking.ts` 分成分词、统计和打分三个步骤。

- 英文按词匹配，拆分 camelCase 和 snake_case，不用任意子字符串命中。
- 连续中文提取相邻双字等词项，过滤一部分常见提问词。
- 文档频率表示“有多少不同片段包含这个词”；IDF 让普遍出现的词权重更低。
- 词频采用 BM25 风格的饱和与长度归一化，避免重复一个词就无限加分。
- 得分主要看加权查询覆盖，再加少量词频与完整短语贡献。

代码中的权重固定为覆盖 75%、词频 15%、短语 10%。
这是可解释的工程组合，不是标准 BM25 原式，也不是经过大规模相关性训练的最优参数。
`explanation` 返回命中词、文档频率和各项贡献，可核对分数。

`textRetriever.ts` 做后续选择：按分数排序，限制 topK 和片段正文预算。
没有任何命中的问题不因为阈值是零就把无关片段送给模型。
缓存版本升到 3，旧索引自动重建，不修改原始上传文件。

这是词法检索，不理解同义词或语义蕴含。得分高不能证明原文支持模型的结论。
后续要不要加向量检索，应先用独立真实问题和标注比较收益与成本。

## 引用：保留可核对的原文

`retrieval/evidence.ts` 根据原始偏移切出片段，缓存行起始位置并二分查行号。
支持 LF、CRLF 和单独 CR；代码解析器只归一化解析输入的单独 CR，
最终引用仍切原文件，不引用归一化副本。

引用标识带文件身份、内容哈希和范围；同名文件不会混用来源。
前端显示经过允许列表筛选的片段，使用 Vue 文本插值，不把文件正文当 HTML 执行。
行号不是 PDF 页码；引用可点开也不等于结论自动正确。

## 验证与基准怎样讲

单元测试覆盖随机混合 Unicode、空白保真、预算、代理对、CRLF、索引迁移、
词频饱和、子字符串误命中、解释分数以及附件异步行为。

本地 Playwright 验收使用模拟模型和合成资料，验证注册登录、图片与文件、
丢失分片 ACK 后补传、取消、恢复、账户隔离以及原文引用。
长列表用 160 条不同高度消息，在五种宽度检查首尾可达、DOM 数量受控、
无消息重叠和输入区不遮挡。截图同时人工检查比例、明暗主题与信息层级。

可选切块基准需要设置 `CHUNKER_BASELINE_PATH` 指向改动前保存的 `chunker.ts`，
以及 `TEXT_BENCHMARK_REPORT` 指定本地输出路径，再运行：

```text
pnpm --filter @ai-tool-chat/worker exec vitest run src/utils/chunker.performance.test.ts
```

本次固定合成文本为 117.6 万 UTF-16 单元，预算 1200，2 次预热、7 次交错采样。
Node v24.13.0 上旧版中位耗时约 576ms、新版约 15.5ms；
旧版 311 块超估算预算且不能还原全文，新版无超限且能还原全文。
这是本地单一合成数据的切块比较，不能写成整个平台加速约 37 倍。
没有验证真实模型答案质量、供应商费用或生产负载。

## 面试时的一分钟讲法

> 我把对话平台重组为可独立阅读的业务模块，并重新设计了工作台界面。
> 长对话采用动态高度虚拟列表，附件异步操作通过代次检查避免写错会话。
> 文件问答先保真切块，再用加权词法匹配选择预算内的片段，最后调用模型。
> 原文引用保存文件哈希、偏移和行号，可以回到上传内容核对。
> 我用单元测试、本地故障注入和切块对照基准验证行为，但不把引用存在
> 当成答案正确，也不把本地切块加速夸大成线上模型响应速度。

练习三件事：手算一块的预算，解释一个 `explanation`，亲自让分片确认失败后补传。
能用代码说明这些取舍，比背一个更复杂的架构名字更重要。
